## 1. 总体结论

**当前工作树已具备 V1 主体骨架，但仍不具备投产条件。**

已经确认存在并基本接通的能力包括：

- 统一 Provider manifest/registry；
- 账号、账号修订及选择历史；
- 来源记录与来源修订；
- OpenList connection、mount、存储目标、binding 和来源 assignment；
- V1 immutable plan、计划 hash 与完整性校验；
- `transfer_executions` 持久执行记录；
- `import_transfer_execute` durable worker 入口与恢复扫描；
- scoped rclone、native transfer、移动 relay、Organizer、final verify、ACK 和 cleanup 门禁；
- 后台账号、位置、规则配置界面和自定义下拉组件。

本轮审计同时确认仍存在三个发布阻断方向：

1. **任务入口未完全收敛**：访客字段禁令误伤可信内部调用，旧 durable task 类型仍处于正式注册状态。
2. **关键组合存在不可达路径**：本地目标开启全局 Organizer 时，Planner 与 Validator 契约冲突。
3. **持久一致性仍有缺口**：认证会话、凭证刷新、账号删除、幂等重试、rclone reconcile 和 execution claim 仍可能造成历史失真、重复副作用或不可恢复状态。

因此，本版本只能视为“架构主体完成、尚待正确性收口”，不能视为已完成生产验收。

## 4. P0：发布阻断问题

### P0-1 访客字段禁令误伤可信内部任务入口

证据：

- `services/import_job_service.py` 的 `ImportJobCreationService.create()` 对所有调用统一拒绝 `destination_id`、`idempotency_key` 等字段；
- `request_approval_service.py` 仍传入 `destination_id` 和 `idempotency_key`；
- `update_candidate_import_service.py` 仍传入 `idempotency_key`；
- `trending_initial_import_service.py` 仍生成并传入 `destination_id`、`idempotency_key`。

影响：

- 访客审批通过后创建任务；
- 追更候选入库；
- 热榜首入库；

均可能直接失败为 `CLIENT_DESTINATION_FORBIDDEN`。这不是边缘问题，而是正式内部业务流程与公共提交防护共用 DTO 造成的契约冲突。

整改：

1. 拆分 Public Submission DTO 与 Trusted Internal Import Command；
2. 访客接口继续拒绝目标、remote、mount、路径和客户端幂等键；
3. 内部命令可以携带内部追踪键，但目标必须由 `search_source_id + category_key` assignment 解析；
4. 对审批、追更、热榜三条真实调用链增加集成测试。

### P0-2 本地目标与全局 Organizer 的计划契约冲突

证据：

- `planning/planner.py` 对 local target 生成本地 staging/final；
- Organizer 开启时又生成 OpenList organizer locator；
- `planning/plan_validator.py` 对非 OpenList staging 只接受 native final，local final 会被拒绝。

影响：

`local target + organizer_enabled` 在 Planner 生成后无法通过 Validator，违背“无论最终保存到哪里，只要开启全局 Organizer 都必须整理”的既定要求。

附带风险：

native/relay Organizer 当前使用分类根路径而非任务级工作目录，并发任务存在串目录和误整理风险。

整改：

- 为 Organizer 明确支持的输入/输出 locator kind 建立统一契约；
- local target 可选择：
  - 在本地任务级 staging 完成 Organizer 后 finalize 到 local final；或
  - 通过受控 OpenList mount 进入 Organizer，但必须冻结真实 mount/identity；
- 所有 Organizer staging 必须带 `job_id` 或 execution-scoped 子目录；
- 增加 local、native、rclone、relay 四类策略开启 Organizer 的矩阵测试。

### P0-3 V1 尚未成为唯一 durable task 真源

`app.py` 仍正式注册：

- `rclone_repair`
- `organizer_process`
- `organizer_apply`
- `media_refresh`
- `media_category_refresh`
- `import_retry`
- `public_import_create`
- `notification_deliver`

V1 的 `import_transfer_execute` 在后部单独注册，其中 `public_import_create` 和 `import_retry` 仍是实际任务入口。

当前证据不足以断言它们一定会导致“双重 Provider 提交”，但它们已经违反“V1 唯一执行真源”的目标，也使恢复、重试、取消与可观测性分散在不同状态机中。

整改：

- 区分非传输型后台任务与入库执行任务；
- 所有会创建或推进 transfer 的旧任务改为只投递/唤醒 canonical execution；
- 删除能够独立推进旧 route/importer 的执行能力；
- 对任务注册表增加白名单测试，确保入库副作用只由 `import_transfer_execute` 推进。

### P0-4 全量回归门禁没有随 V1 hard cutover 收敛

当前全量测试为 111 failure、106 error。命名最集中的四个模块合计 90 failure、13 error，说明测试体系仍同时描述三套互相冲突的契约：

- 旧 V2/V3/legacy staging 恢复行为；
- 已 hard cutover 的 canonical V1 行为；
- 没有 V1 plan/revision 的半迁移 fixture。

典型例子：

- `test_callback_ack_semantics` 的 job 没有 immutable V1 plan，52 个断言全部在 guard 层收到 409，未真正验证取消、晚到回调和 delete ACK；
- `test_staging_retry_limits` 仍要求恢复 `test_v3_*` 和无 staging plan 的 legacy job；
- `test_rclone_persisted_staging_plan` 仍调用已禁用的旧入口；
- 当前 relay contract 明确禁止 `destination_staging`，部分 V1 测试和设计说明仍按旧字段构造计划。

影响：即使部分 V1 定向测试通过，也没有可信的全量回归门禁证明重构没有破坏回调、取消、恢复、Organizer 和 cleanup。

整改：

1. 建立测试清单，将每个红灯标注为“删除旧兼容测试 / 迁移到 V1 fixture / 真实生产缺陷 / 环境阻断”；
2. 删除明确要求 V2/V3 回放的测试，替换为“旧计划失败关闭”的 V1 测试；
3. 建立统一 V1 job/plan/execution fixture factory，禁止测试直接伪造半份 raw_data；
4. 先让 callback ACK、取消 fence、recovery、Organizer、rclone descriptor 四个核心矩阵全部绿，再运行全量；
5. CI 在 Linux/容器中将全量测试设为发布硬门禁，不允许只报告定向测试通过。

## 5. P1：正确性与持久一致性问题

### P1-1 标准 magnet infohash 解析错误

`planning/source_resolver.py::_magnet_xt()` 直接按 `&` 拆分并寻找 `xt=`。标准 URI 第一段是 `magnet:?xt=...`，因此无法命中。

影响：同一 infohash 仅 tracker 参数不同就可能得到不同 canonical source ID，破坏去重和幂等。

整改：使用 `urlsplit`/`parse_qsl` 解析 query，规范化 hex/base32 infohash，并增加参数顺序、大小写、tracker 差异测试。

### P1-2 rclone reconcile 查询不确定时仍可能重新提交

`transfer/rclone_adapter.py` 在查询历史 run 抛异常时继续尝试，最终可能返回 `None`；`start_copy()` 会把它解释为“没有旧 run”并再次提交。

影响：数据库或 rclone 服务短暂异常时，可能重复执行跨盘复制。

整改：reconcile 必须 fail-closed。只允许“明确不存在”进入 submit；查询异常进入 retry/deferred，无法确定时进入 manual review。

### P1-3 凭证 refresh 没有绑定冻结账号 revision

`accounts/service.py` 的 refresh 路径只接收 `account_id`，读取并更新当前 revision；Composition Root 中 Quark/Tianyi/SixPan 的 callback 也只捕获 account ID。

影响：旧执行计划刷新凭证时可能修改后来切换的当前账号 revision，而冻结旧 revision 仍然失效，形成“任务用旧凭证、刷新写新凭证”的分裂。

整改：callback 必须携带 `expected_revision`；采用 CAS 创建后继 revision，或者维护 execution-scoped credential lease。不得隐式推进无关当前选择。

### P1-4 Auth Session 缺少事务、CAS 和终态清密

`accounts/auth_sessions.py` 当前存在：

- 账号创建/激活与 session 插入非同一事务；
- poll 没有 row version/CAS，并发 poll 可重复生成账号修订；
- 缺少 provider + auth method 的活跃 session 唯一约束；
- completed/failed/cancelled 后仍保留 encrypted private state；
- private state 可能含天翼账号密码、六盘 secret/device code；
- expire 与 poll 存在并发更新窗口。

整改：

- 增加 session version 和 compare-and-swap；
- 增加活跃 session 约束；
- 账号修订与 session 终态在同一事务提交；
- 所有终态清空 private state，仅保留脱敏审计字段；
- 并发 poll、重复 verify、expire/poll 竞争必须有测试。

### P1-5 完成或取消后物理删除账号会破坏历史计划

`accounts/repository.py` 允许 execution phase 为 `completed` 或 `cancelled` 时物理删除账号及全部 revision。

但 `import_execution_plans` 永久冻结账号 revision。删除后，完成任务也无法复核计划、验证 receipt 或审计历史。

整改：账号使用软删除；revision 永久保留或按合规策略归档。禁止删除被 immutable plan 引用的 revision。

### P1-6 manual_review/cancelled 后无法重新入库相同资源

当前 job idempotency key 永久命中旧任务，source revision 会被复用，而 execution repository 禁止重新激活 `manual_review`、`cancelled`。

影响：管理员无法对同一资源、选集、分类、目标和账号 revision 做合法重试。

整改：定义明确的 execution generation / retry generation；重新入库应创建新 execution，并保留与旧 execution 的 lineage。禁止简单清除旧幂等记录。

### P1-7 来源 inspect 与服务端选集校验未闭环

生产 Planner 创建前没有稳定调用 Provider `inspect_source()` 来确认：

- 分享链接和密码有效；
- selected item、ignore_files 确实属于该分享；
- expected file count/size 来源可信。

同时，有 `public_id` 时复用缓存 source record，可能丢弃本次提交的密码或 Provider 选集。

整改：

- 合并可信缓存字段与允许的本次 password/selection；
- 使用冻结前的活动来源账号执行 `inspect_source()`；
- 将服务端确认后的 locator、selection、文件数量和大小冻结进 source revision/plan；
- 对缓存过期、密码变化、选集越权增加失败测试。

### P1-8 job 幂等身份与 immutable plan 存在 revision 分裂窗口

`ImportJobCreationService.create()` 在事务前解析 destination/source account 并生成 job idempotency identity，Planner 随后又读取 assignment、account、binding、target；传入的 destination 没有成为 Planner 的唯一 routing snapshot。

影响：配置在两次读取之间切换时，job idempotency key 可能引用旧 revision，而 immutable plan 冻结新 revision。

整改：在同一数据库事务内生成一次不可变 routing snapshot，并直接传给 Planner；或者对全部 revision 做 CAS/version 校验后提交。

### P1-9 receipt alias 匹配范围过宽

`transfer/execution_repository.py` 会把 `landing:`、`relay-dl:`、`relay-up:` 三类 operation key 去前缀后加入同一 alias 集合。

影响：不同副作用 leg 可能因相同 base key 被错误视为同一次提交。

整改：receipt fence 按 phase、strategy、side-effect kind 和完整 operation key 精确匹配；旧格式兼容只能做显式、单向迁移。

### P1-10 execution claim 没有独立心跳

`transfer/dispatch.py` 的 execution claim 默认租约为 600 秒。长时间 Provider/rclone 调用期间没有 execution-level heartbeat，worker task heartbeat 也未与 execution claim 绑定。

影响：调用超过 lease 后，另一个 Worker 可能接管同一 execution。

整改：外部调用期间续租 execution claim，并使用 owner token + version CAS；失去租约的 worker 禁止再提交状态。

### P1-11 任务详情缺少 durable transfer execution 视图

`services/job_service.py` 返回 events、guest requests、rclone events、Organizer 和 worker tasks，但没有完整展示：

- phase、strategy；
- receipt；
- attempt、resume_at；
- staging/final verify；
- organizer_task_id；
- ACK、cleanup；
- last_error。

影响：管理员无法判断任务卡在 Provider、rclone、Organizer、ACK 还是清理阶段。

整改：增加脱敏的 execution view，并在后台任务详情中用状态时间线展示。

### P1-12 OpenAPI 未覆盖 V1 管理路由

当前 OpenAPI 仍主要覆盖旧管理接口。账号、认证会话、OpenList connection/mount、存储目标、binding、assignment、storage setup/routing matrix 等 V1 管理路由未完整声明。

本轮扫描确认缺少 32 个 V1 路径，现有 `test_openapi_admin_routes` 通过不代表 V1 API 契约完整。

整改：从 Blueprint 路由生成或集中维护 OpenAPI，增加“所有 /api/admin V1 路由必须在 spec 中存在”的集合对比测试。

### P1-13 Provider 扩展仍需修改核心 Composition Root

Registry 和 entry-point 已存在，但下列位置仍硬编码四类 Provider：

- `app.py` 的 auth handler 装配；
- `app.py` 的 `_provider_importer`；
- built-in Adapter 注册；
- `transfer/native_executor.py` 的 `LegacyNativeAdapter` provider 分支。

影响：新增 115 仍需修改核心装配和 legacy adapter，不符合“新增 manifest + Adapter + 搜索映射 + 契约测试即可扩展”。

整改：manifest/adapter factory 同时提供 auth strategy、importer/client factory 和 capability handler；Composition Root 只遍历注册表，不识别具体 provider kind。

## 6. P2：可用性与运维问题

### P2-1 管理页面导航层级过多

当前页面同时存在：

- 系统级导航；
- 多链路步骤导航；
- 账号/位置/规则子导航；
- 卡片内部动作区。

用户需要理解过多概念，账号、位置、目标和来源路由之间的关系不直观。

建议收敛为三个工作区：

1. 账号中心：登录、检测、激活、禁用；
2. 保存位置：OpenList 连接、挂载与存储位置；
3. 入库规则：按来源选择默认保存位置。

高级 binding、revision、identity 等概念只在“高级信息”中展示，不要求普通管理员逐项配置。

### P2-2 移动端横向溢出和嵌套滚动

在 390×844 视口中，`.admin-tabs` 的 scroll width 约 1150px；`#tab-adapters` 使用固定高度内部滚动，桌面和移动端均形成页面滚动 + 面板滚动。

整改：

- 移动端将顶级导航改为可折叠菜单或两行网格；
- 去掉主要内容区固定高度；
